01 Testing Strategy

Architecture & execution model

The UI suite is built as a black-box client against the running qAcademy application — it drives the real browser against the real Spring Boot server and H2 database, the same way a person would. Four ideas hold the framework together:

▤Page Object Model

Every screen — LoginPage, StudentsPage, CoursesPage, EnrollmentsPage, RegisterPage — is one class owning its own locators and actions. Tests read as user intent (studentsPage.addStudent(...)), never as raw By selectors.

The top navigation bar is factored out once into a NavBarComponent and reused by every page object, since it's identical chrome on every screen after login.

◷Explicit, condition-based waits

Every page extends a shared BasePage that wraps Selenium's WebDriverWait: type, click, and read actions all wait for the real DOM condition they need, rather than a fixed sleep.

A dedicated bounded-wait check (isVisibleWithinWait) is used anywhere a test asks "did this appear after that action" — the app renders its confirmation and error banners asynchronously, so a single instantaneous check would race the network call.

⇄Thread-safe driver lifecycle

A Factory Method (DriverFactory) builds the browser named in config.properties; a ThreadLocal-backed DriverManager hands each test thread its own private instance, so the suite is safe to run in parallel without one test's clicks landing in another's browser.

✳Collision-free test data

A single TestDataFactory builds every valid and invalid payload. Because the H2 database is a persistent file — not reset between runs — every "valid" record is stamped with a fresh UUID suffix, so re-running the suite ten times never trips over yesterday's email address.

⟲Resilience & reporting

A RetryAnalyzer gives a genuinely flaky test one second attempt before it's recorded as failed. A TestNG ITestListener logs every outcome to ExtentReports and attaches a screenshot automatically the moment a UI test fails.

☰Suite orchestration

Five TestNG XML suites separate concerns: smoke (one happy path per screen), ui, api, e2e, and regression (the full combined run) — so a two-minute confidence check and a full pass are both a single Maven command away.

03 Test Design Method

How each case earns its place

No test case exists just to pad a count. Each one was chosen against a specific design technique, listed below with where it shows up in the catalog.

01

Equivalence Partitioning

Every input — credentials, dates, emails, credit values — is tested with one representative from its valid class and one from its invalid class, not every possible value.

02

Boundary Value Analysis

Course credits at 7 (one past the backend's real cap of 6, but still inside the form's own max of 12) and calendar-edge dates like 31 April pin exact edges rather than obviously-wrong values.

03

Negative & Error-Path Testing

Wrong password, an impossible date, an over-limit credit value — each confirms the system fails safely, with the right message, and without side effects.

04

Role-Based Access Control (RBAC)

Admin, Staff, and Student each get a distinct permission matrix, checked twice: once as a UI affordance (is the button even rendered) and once as a server rule (does the API reject it anyway).

05

State-Transition Testing

An enrollment's grade moves from "Ungraded" to a letter grade; a row moves from present to deleted. Each transition is asserted on both sides, not just the end state.

06

Cross-Layer (Hybrid) Integration

Data is created in one layer and verified in the other — API-created data must appear in the UI, UI-created data must be readable by the API — proving both layers share one true source of record.

Cross-Layer Flows

5 cases

Covers CrossLayerFlowTest — scenarios that deliberately cross the UI/API boundary to prove the two layers agree.

E2E-01

A newly self-registered Staff account can manage Students but not Courses

Registration, login, and RBAC checked together, at both layers — the API is asked to perform the same rejected write directly, to rule out a UI-only illusion of security.

RBAC
Steps

  2. Log in as that account; confirm the add-student form is visible.
  3. Navigate to Courses; confirm the add-course form is hidden.
  4. Send the same course-create request directly to the API with that account's token.
UI shows write access to Students, read-only to Courses; the direct API call independently returns 403.

E2E-02

A student created via the API appears in the UI roster

Proves there is one source of truth: data written through the raw API must be readable through the UI without any special-casing.

Cross-Layer
Steps
  1. Create a student directly via the API.
  2. Log into the UI as Admin and open the Students roster.
The API-created student's row is present in the UI table.
Maps to: e2e02_studentCreatedViaApi_appearsInUiRosterOnNextLoad
E2E-03

A grade stays Ungraded until Admin sets it via the API

A full role-swapping workflow: Admin creates via UI, Staff enrolls via UI, and only Admin's direct API call is allowed to move the grade — the UI must reflect that change after a refresh.

Cross-Layer
Steps
  1. As Admin, add a student and a course through the UI.
  2. Log out; log in as Staff and enroll that student into that course through the UI.
  3. Confirm the grade badge reads "Ungraded".
  4. As Admin, set the grade directly via the API.
  5. Refresh the Staff session's Enrollments page.
Grade badge updates to the API-set value after the refresh.
Maps to: e2e03_enrollmentGrade_staysUngradedUntilAdminSetsItViaApi
E2E-04

Deleting a student via the UI cascades to their enrollments

A referential-integrity requirement (NFR-05): removing a student must not leave orphaned enrollment records behind — verified by asking the API directly after the UI delete.

Cross-Layer
Steps
  1. Seed a student, a course, and an enrollment between them via the API.
  2. Delete the student through the UI.
  3. Query the API for that student's enrollments.
Roster row disappears in the UI, and the API reports zero remaining enrollments for that student.
Maps to: e2e04_deletingStudentViaUi_cascadesToDeleteTheirEnrollments
E2E-05

The server rejects an unauthorized write even though the UI never renders the button

Confirms hiding a control is a UI convenience, not the actual security boundary — a Student account is tested at both layers, plus a request with no token at all.

RBAC
Steps
  1. Log in as Student; open Courses and confirm the add-course form is absent.
  2. Send a course-create request directly to the API using the Student's own valid token.
  3. Repeat the same request with no token at all.
UI never renders the form; both direct API calls independently return 403.

05 Defects This Suite Actually Caught

Evidence the design earns its keep

A test plan is only as good as what it finds. Three real, production-affecting defects surfaced directly through these UI and cross-layer cases during this project — each is fixed now, but is left here as a record of why the coverage above exists.

Valid birth dates were rejected by the server

found via UI-STU-01 / UI-STU-02
SymptomAdding a student with a perfectly ordinary date of birth failed with "not a real calendar date" — every time, for every date.
Root causeThe backend's date parser used the pattern letter for "year-of-era" instead of "year", which Java's strict date parser can't resolve without an explicit era — so it rejected every date, valid or not.
FixCorrected the pattern in both the create and update validators; verified against real leap-year and impossible-date edge cases before shipping the fix.

Newly created students/courses were invisible on the Enrollments screen

found via UI-ENR-01
SymptomA student seeded moments earlier couldn't be selected in the enrollment form's dropdown — the option simply didn't exist.
Root causeThe Enrollments screen reused an in-memory cache of the student/course lists first populated by the Home dashboard, instead of fetching fresh data for its own dropdowns.
FixEnrollments now always fetches current data, matching how every other screen in the app already behaved.

"Reopening" a page you're already on silently did nothing

found via UI-STU-03
SymptomA student created via the API right before the roster was reopened still didn't appear in the table.
Root causeThe app routes by URL hash; clicking a nav link to the route you're already on doesn't change the hash, so the router's hashchange listener never re-fires and the page never re-fetches.
FixThe test now forces a real browser refresh to reload the route, rather than relying on a same-route navigation click.
