01 Shared Foundation

What the UI and API suites build on together

The UI and API suites are two different clients of the same application, but they share one skeleton underneath: the same test data, the same reporting pipeline, and the same suite orchestration. That's deliberate — a defect found by an API test and a defect found by a UI test show up side by side in one report, not two.

✳One test data factory

TestDataFactory builds every valid and invalid payload used by both lanes. Because the H2 database is a persistent file — never reset between runs — every "valid" record carries a fresh UUID suffix, so the same suite can run a hundred times without tripping over its own leftover data.

☰One suite orchestration

Five TestNG XML files — smoke, ui, api, e2e, and the combined regression — let a two-minute confidence check or a full pass run from a single Maven command, mixing or isolating either lane at will.

⟲One resilience & reporting layer

A shared RetryAnalyzer gives a genuinely flaky test one second attempt. A single TestNG ITestListener logs every UI and API outcome into one ExtentReports HTML report, screenshotting UI failures automatically.

02 UI Testing Strategy

Architecture & execution model

The UI suite is a black-box client against the running qAcademy application — it drives a real browser against the real Spring Boot server and H2 database, the same way a person would.

▤Page Object Model

Every screen — LoginPage, StudentsPage, CoursesPage, EnrollmentsPage, RegisterPage — is one class owning its own locators and actions. Tests read as user intent (studentsPage.addStudent(...)), never as raw By selectors.

The top navigation bar is factored out once into a NavBarComponent and reused by every page object, since it's identical chrome on every screen after login.

◷Explicit, condition-based waits

Every page extends a shared BasePage wrapping Selenium's WebDriverWait: actions wait for the real DOM condition they need, never a fixed sleep.

A bounded-wait check (isVisibleWithinWait) is used anywhere a test asks "did this appear after that action" — the app renders confirmations and errors asynchronously, so one instantaneous check would race the network call.

⇄Thread-safe driver lifecycle

A Factory Method (DriverFactory) builds the browser named in config.properties; a ThreadLocal-backed DriverManager hands each test thread its own private instance, safe for parallel execution.

04 UI Test Design Method

How each case earns its place
01

Equivalence Partitioning

Every input — credentials, dates, emails, credit values — gets one representative from its valid class and one from its invalid class.

02

Boundary Value Analysis

Course credits at 7 (past the backend's real cap of 6, but inside the form's own max of 12) and calendar-edge dates pin exact edges, not obviously-wrong values.

03

Negative & Error-Path Testing

Wrong password, an impossible date, an over-limit credit value — each confirms the system fails safely, with the right message, and no side effects.

04

Role-Based Access Control

Admin, Staff, and Student each get a distinct permission matrix, checked as a UI affordance and, in the cross-layer cases, as a server rule too.

05

State-Transition Testing

An enrollment's grade moves from "Ungraded" to a letter grade; a row moves from present to deleted — each transition is asserted on both sides.

06

Cross-Layer (Hybrid) Integration

Data created in one layer is verified in the other, proving both layers share one true source of record.

06 Defects the UI Suite Caught

Evidence the design earns its keep

Valid birth dates were rejected by the server

found via UI-STU-01 / UI-STU-02
SymptomAdding a student with a perfectly ordinary date of birth failed with "not a real calendar date" — every time, for every date.
Root causeThe backend's date parser used the pattern letter for "year-of-era" instead of "year", which Java's strict date parser can't resolve without an explicit era.
FixCorrected the pattern in both validators; re-verified against real leap-year and impossible-date edge cases.

Newly created students/courses were invisible on the Enrollments screen

found via UI-ENR-01
SymptomA student seeded moments earlier couldn't be selected in the enrollment form's dropdown.
Root causeThe Enrollments screen reused an in-memory cache of the student/course lists first populated by the Home dashboard.
FixEnrollments now always fetches current data, matching every other screen.

"Reopening" a page you're already on silently did nothing

found via UI-STU-03
SymptomA student created via the API right before the roster was reopened still didn't appear.
Root causeThe app routes by URL hash; clicking a nav link to the route you're already on never changes the hash, so the router's hashchange listener never re-fires.
FixThe test now forces a real browser refresh instead of a same-route navigation click.

02 API Testing Strategy

Architecture & execution model

The API suite talks HTTP directly to qAcademy's REST layer with RestAssured — no browser involved — so it can reach validation rules and role rules the UI never lets a person trigger by accident, and pin the exact shape of every response, not just its status code.

▤API Client Object Model

One class per resource — AuthApiClient, StudentApiClient, CourseApiClient, EnrollmentApiClient — mirrors the UI's Page Object Model: a test reads as studentApiClient.createStudent(...), never as an inline RestAssured chain.

⎘One shared request spec

RequestSpecFactory builds a single RestAssured RequestSpecification — base URI, JSON content type, request/response logging — once. Every client asks this factory instead of repeating given().baseUri()... in every method.

◈Typed, immutable payloads

Request and response bodies are Java records (StudentCreateRequest, CourseResponse…), so a payload is built and read with compile-time-checked fields instead of loose JSON-path strings scattered through the tests.

🔑Token-based RBAC verification

Every protected client method takes a bearer token. Tests fetch real JWTs for Admin, Staff, and Student through the same login endpoint under test, then assert the exact status each role must receive.

▧Response-shape contract testing

qAcademy deliberately returns three different error shapes: a raw JSON array of strings from field validators, a {"message": "..."} object from service-layer failures, and an empty body from a 404. Tests assert the exact shape, not only the status code.

⟲Shared infrastructure

The same TestDataFactory, ExtentReports pipeline, RetryAnalyzer, and TestNG suite files back the API lane too — see Shared Foundation above.

04 API Test Design Method

How each case earns its place
01

Equivalence Partitioning

Every field — password length, role name, email shape, credit value — gets one representative from its valid class and one from its invalid class.

02

Boundary Value Analysis

Credits at exactly 0, exactly 6 (the real cap), and exactly 7 (one past it) pin the precise edge the validator enforces.

03

Authorization Matrix Testing

Every write endpoint is called with an Admin token, a Staff token, and a Student token in turn, asserting the exact status (201 or 403) each role must get — including asymmetries, like Staff being allowed to create a Student but not a Course.

04

Non-Existent-Resource Testing

IDs like 999999999 probe delete/update endpoints for the correct 400 vs 404 behavior depending on whether the resource is a foreign key or the target itself.

05

Response-Contract Testing

The exact JSON shape is asserted, not just the status code — a validator failure's raw string array, a service failure's {"message":...} object, and a 404's genuinely empty body are three different contracts, each pinned separately.

06

State & Field-Level Verification

A newly created enrollment must carry a null grade; a grade only moves via its own PUT endpoint — verified as an explicit assertion, not assumed.
