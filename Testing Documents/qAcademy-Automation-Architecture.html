qAcademy Automation Architecture

One TestNG suite, two independent lanes. UI tests drive the real browser through Selenium; API tests call /api/** directly through RestAssured — both exercise the same running qAcademy Spring Boot app and the same H2 file database, and both report through one shared ExtentReports instance.

UI Automation Lane

Page Object Model classes wrapping Selenium. Tests never call WebDriver/By directly — only page methods.

API Automation Lane

One Service Client class per resource (StudentApiClient, CourseApiClient, …), built on a shared RestAssured request spec.

Shared Support Layer

Config, wait helpers, JSON helpers, logging and the TestNG listener that feeds ExtentReports — used identically by both lanes.

Reporting

One ExtentReports HTML file per run, regardless of whether the run mixed UI, API, or hybrid end-to-end tests.

One decision to settle first: src/main vs src/test

You asked to combine the automation framework into the same qAcademy project rather than a separate one — a reasonable call for a solo/portfolio project, and this design honors it. But it changes where the framework code should live compared to what you first described.

You suggested framework classes (Page Objects, API clients, utilities) go under src/main/java, with only @Test classes under src/test/java. That's correct for a standalone automation Maven module — but here, src/main/java/com/qacademy/... is already your production Spring Boot application, the code compiled into target/qacademy.jar.

Selenium, RestAssured, and ExtentReports should be declared test-scoped — exactly like the testng and mockito-core dependencies already in your pom.xml. A test-scoped dependency only exists on the test classpath. A Page Object under src/main/java importing org.openqa.selenium.* simply wouldn't compile unless Selenium were promoted to compile scope — which would then ship Selenium, RestAssured, and ExtentReports inside your production application jar. That bloats the deployable, mixes test tooling into production dependencies, and risks version conflicts with the app's own dependencies.

Resolution: everything automation-related — framework classes and test classes alike — lives under src/test/java (and src/test/resources), in its own package namespace (com.qacademy.automation) so it's structurally distinct from com.qacademy.core / .infrastructure / .api even though it's the same Maven module. This is exactly how Spring Boot's own @SpringBootTest integration tests are organized — one repo, one pom.xml, one mvn clean install, with the production artifact staying completely clean.

Maven changes needed

Add these to the existing <dependencies> block — all test scope, consistent with your existing testng/mockito-core entries. 

<!-- UI automation -->
<dependency>
    <groupId>org.seleniumhq.selenium</groupId>
    <artifactId>selenium-java</artifactId>
    <version>4.27.0</version>
    <scope>test</scope>
</dependency>

<!-- API automation -->
<dependency>
    <groupId>io.rest-assured</groupId>
    <artifactId>rest-assured</artifactId>
    <version>5.5.0</version>
    <scope>test</scope>
</dependency>

<!-- Reporting -->
<dependency>
    <groupId>com.aventstack</groupId>
    <artifactId>extentreports</artifactId>
    <version>5.1.2</version>
    <scope>test</scope>
</dependency>

No WebDriverManager needed — Selenium 4.6+ ships Selenium Manager, which resolves the right ChromeDriver/GeckoDriver automatically. No extra JSON library needed either — Jackson already arrives transitively via spring-boot-starter-web, and your API models will read almost identically to the app's own DTOs (StudentDto, CourseDto, …) on purpose, so the mapping is obvious at a glance. TestNG (7.12.0) is already present and auto-detected by Surefire — a <suiteXmlFiles> block becomes worth adding once the testng-*.xml suites below exist.

Java concepts this framework deliberately leans on

What, and — more importantly — why, so each choice is something you can explain, not just use.

ConceptWhere it shows upWhy it's the right tool here
Page Object Model ui/pages/* Encapsulation applied to UI testing: locators and low-level Selenium calls live in one place per screen; tests only call intention-revealing methods, so a UI change means editing one class, not every test that touches that screen.
Inheritance BaseTest → BaseUiTest/BaseApiTest; BasePage → concrete pages Shared setup/teardown and helpers live once at the top of the hierarchy instead of copy-pasted into every class.
Factory Method DriverFactory.createDriver(BrowserType) Test code asks for "a Chrome driver" without knowing how it's constructed — swapping in Firefox later is a one-line change, not a find-and-replace.
Singleton ExtentReportManager, ConfigManager Exactly one ExtentReports instance must exist per run — it's the one HTML file being written to — and exactly one loaded copy of config.properties.
ThreadLocal<WebDriver> DriverManager The single concept that makes parallel UI execution safe. A plain static WebDriver field would let two threads silently drive the same browser session; ThreadLocal gives each thread its own instance.
Builder pattern RestAssured's given()...when()...; your own TestDataFactory Reads as a sentence — and matching the main app's "no Lombok, nothing hidden" philosophy, your builders are hand-written, so every line is explainable.
Fluent interfaces Page Objects returning the next page (e.g. loginPage.loginAs(ADMIN) returns a HomePage) A test reads like a story, and the compiler catches a broken navigation assumption immediately via the return type.
Enums UserRole, Environment, BrowserType Type-safe constants instead of raw strings — UserRole.ADMIN can't be typo'd, and each constant can carry its own data.
Interfaces An ApiClient contract; optionally a Page interface Lets shared code depend on a contract, not a concrete class — useful the moment a second implementation shows up (e.g. a mock client for offline dev).
Custom exceptions FrameworkException Turns a raw NoSuchElementException into a message that says what business action failed — exactly what shows up in the ExtentReports failure log.
ITestListener TestListener TestNG discovers listeners declared in testng.xml via reflection and calls them at lifecycle points — the wiring between "a test failed" and "log it, screenshot it, write it to ExtentReports," with none of that logic inside the test classes.
Deterministic cleanup @AfterMethod in BaseUiTest A browser session must close even when the test above it threw — cleanup runs whether the test passed or failed.
Streams / lambdas tests/e2e/* Where "combine UI and API" becomes real code: comparing a list scraped from the UI table against apiClient.getStudents().stream().map(...) — the literal mechanism behind "one source of truth."

Step-by-step build order

Each step is independently reviewable before moving to the next — say which one you want implemented first.

  1. Add the three Maven dependencies (selenium-java, rest-assured, extentreports).
  2. Config layer: Environment enum, ConfigManager (Singleton).
  3. UI foundation: DriverFactory + DriverManager (ThreadLocal<WebDriver>).
  4. API foundation: RequestSpecFactory + BaseApiClient.
  5. Base test hierarchy: BaseTest → BaseUiTest / BaseApiTest.
  6. Utilities: WaitUtils, JsonUtils, ScreenshotUtils, LoggerUtil.
  7. Reporting: ExtentReportManager (Singleton) + TestListener.
  8. API models: request/response POJOs, field-matched to the app's own DTOs.
  9. API clients: AuthApiClient, StudentApiClient, CourseApiClient, EnrollmentApiClient.
  10. UI Page Objects: LoginPage → HomePage → StudentsPage/CoursesPage/EnrollmentsPage + NavBarComponent.
  11. Test data: TestDataFactory + UserRole enum.
  12. First smoke tests: one UI login test, one API login test — proves the wiring end-to-end.
  13. Fill out the suites: remaining API tests → remaining UI tests → CrossLayerFlowTest.
  14. testng-*.xml suite files: smoke / ui / api / e2e / regression.
  15. Confirm ExtentReports output end-to-end on a full regression run.
  16. Later, per your stated intention: layer BDD (Cucumber + Gherkin) on top of the same Page Objects and API clients, so step definitions become thin wrappers rather than a rewrite.
