qAcademy Project Guide

A complete, end-to-end explanation of the qAcademy application itself — what it is, how every layer is built, why it's built that way, and how to install, run, and use it. Written to be readable by both engineers and non-technical readers.

Java 17 Spring Boot 3.5 H2 + Flyway JWT Auth Vanilla JS Dashboard Maven
01

Overview

What qAcademy is, and why it exists

PIn plain English

qAcademy is a small web application for running a school's day-to-day records: who the students are, what courses exist, and who is enrolled in what — including their grades once assigned. It works the way a lot of real internal business software works: a sign-in screen, a dashboard, and a few pages for adding and viewing records. Three kinds of people can use it — an Admin who can do everything, Staff who can manage students and enrollments but not the course catalog, and a Student who can only look, not change anything.

TTechnical framing

qAcademy is a full-stack, single-deployable school management system: a layered Java/Spring Boot REST API secured with hand-rolled JWT authentication, backed by a file-mode H2 database with Flyway migrations, paired with a same-origin, dependency-free vanilla JavaScript single-page dashboard. There is no separate frontend build, no CORS configuration, and no external services — mvn spring-boot:run is the entire deployment story.

The project was built as a portfolio / learning piece to demonstrate a complete, honest layered architecture with nothing hidden behind framework magic — no Lombok, no Jakarta Bean Validation annotations, hand-written validators and getters/setters instead. It's the Java/Spring Boot member of a three-language series: qEducation and qCampus are .NET implementations of the exact same domain and decisions, built to practice and demonstrate the same architectural thinking across stacks.

This document covers the application itself — every layer, every endpoint, every page. The automation test suite that exercises this application (Selenium + RestAssured + TestNG) is documented separately in the qAcademy Test Blueprint.

Architecture

How the backend is organized, and how a request travels through it

qAcademy is one Maven module, but the Java code is split into three packages that each play a distinct role — this is package-based layering, a lighter-weight alternative to splitting the code into several separate Maven modules, appropriate for a deployable of this size.

com.qacademy.api
The HTTP boundary. controller/ — the four @RestController classes that receive requests. security/ — JwtAuthenticationFilter, which reads the Bearer token on every request. config/ — SecurityConfig, which wires the whole security filter chain and the URL permission rules.
▲ calls down into ▼
com.qacademy.core
The domain contracts. entity/ — the four JPA entities (Student, Course, Enrollment, User). dto/ — the request/response shapes controllers actually talk in (never raw entities). service/ — plain interfaces (StudentService, CourseService, EnrollmentService, AuthService) that describe what each module can do, without saying how.
▲ implemented by ▼
com.qacademy.infrastructure
repository/ — Spring Data JPA repository interfaces (database access). service/ — the *ServiceImpl classes that actually implement the core.service interfaces. security/ — JwtUtil (token issuing/parsing). validation/ — hand-written Validator classes. config/ — DataSeeder (demo accounts) and PasswordEncoderConfig (BCrypt bean).
TWhy an interface in core, an implementation in infrastructure?

A controller depends on StudentService (the interface), never on StudentServiceImpl directly. That's what makes unit testing possible without a real database — a test constructs a service with a Mockito mock of its repository dependency instead of Spring Data's real generated implementation. It's the same reasoning that justifies a Repository pattern on top of an ORM: the abstraction is what gets substituted in tests.

How one request actually travels through the app

Take POST /api/student as a concrete example — an Admin adding a new student from the dashboard:

Browserfetch() with a Bearer token
→
JwtAuthenticationFiltervalidates the token, populates SecurityContext
→
Spring Securitychecks @PreAuthorize("hasAnyRole('ADMIN','STAFF')")
→
StudentControllerdeserializes JSON to StudentCreateDto
→
StudentCreateValidatorchecks the DTO, returns errors or nothing
→
StudentServiceImplmaps DTO → entity
→
StudentRepositorySpring Data JPA saves it
→
H2 file DB./data/qacademy.mv.db

The response DTO is mapped back up the same chain in reverse: entity → StudentDto → JSON → 201 Created back to the browser.

One request path skips almost all of this: the dashboard's own files. SecurityConfig explicitly permitAlls /, /index.html, /css/**, and /js/**, so the browser can load the login page itself with no token and no filter logic involved — only the API calls that page later makes go through the chain above.

Domain Model

The four tables, and how they relate

PIn plain English

A student can be enrolled in many courses, and a course can have many students in it — that's a many-to-many relationship. But an enrollment itself carries information that belongs to neither the student nor the course alone: the date they enrolled, and the grade they got. So instead of a plain "linking table," qAcademy makes Enrollment its own real thing with its own data — this is a very common, very interview-relevant pattern.

Two indexes, and why

idx_enrollments_student_id and idx_enrollments_course_id exist because both "all enrollments for this student" and "all enrollments for this course" are real, used queries (EnrollmentRepository.findByStudentId / findByCourseId) — without an index, both would force a full table scan as the enrollments table grows.

Where the schema comes from

The entire schema is created by one Flyway migration, src/main/resources/db/migration/V1__init.sql, run automatically on startup. application.properties sets spring.jpa.hibernate.ddl-auto=validate — Hibernate does not auto-generate or alter tables; instead it checks the @Column mappings in the Java entities against whatever Flyway already created, and fails fast at startup if they disagree (for example, a typo'd column name is caught immediately, not on the first query that touches it).

The migration also seeds two courses (Algebra I, US History) and one student (Ada Lovelace) directly in SQL. The three login accounts (admin / staff / student) are not seeded here — see DataSeeder in Authentication for why.

Security & Authentication

How qAcademy knows who you are, and what you're allowed to do

PIn plain English

When you sign in, the server hands your browser a signed digital token — a JWT (JSON Web Token). Your browser keeps that token and shows it on every request it makes afterward, like a wristband at an event. The server checks the wristband is genuine and reads your role off it (Admin, Staff, or Student) to decide what you're allowed to do, without needing to remember who's signed in between requests.

The login flow

1. Sign inPOST /api/auth/login {username, password}
→
2. AuthServiceImplBCrypt-matches the password against the stored hash
→
3. JwtUtilissues an HS256 JWT: {sub, username, role}, 2h expiry
→
4. Browserstores {token, username, role} in sessionStorage
→
5. Every later requestAuthorization: Bearer <token>

On every request: JwtAuthenticationFilter

This filter runs once per request (it extends OncePerRequestFilter), before Spring Security's own authentication step. It reads the Authorization header; if it finds a valid Bearer token, it parses the claims and populates Spring Security's SecurityContext with a ROLE_<ROLE> authority. If the token is missing, expired, or invalid, it simply clears the context and lets the request continue unauthenticated — the actual rejection (401/403) happens downstream, at the URL/method authorization rules, not inside this filter.

TGotcha: why this filter is not a @Component

Any Spring bean assignable to Filter gets auto-registered by Spring Boot as a blanket servlet filter, applied to every request, in addition to however Spring Security itself wires it in via addFilterBefore(). Making JwtAuthenticationFilter a @Component would run it twice per request. SecurityConfig avoids this by constructing it directly with new JwtAuthenticationFilter(jwtUtil) and wiring it into the filter chain by hand — a well-documented Spring Security gotcha worth knowing outside this project too.

Role-based authorization (RBAC)

Method-level @PreAuthorize annotations on each controller method are the actual enforcement point — never the dashboard's own hidden buttons, which are a UX convenience only.

GET endpoints on students, courses, and enrollments are deliberately left open (permitAll) rather than requiring a token — a demo/portfolio choice, so anyone can see the app "doing something real" without first creating an account.

!Statelessness

SecurityConfig disables CSRF protection and sets SessionCreationPolicy.STATELESS — there is no server-side session at all. This is standard and correct for a pure token-based API: CSRF protection exists to defend session-cookie auth, which this app doesn't use.

Module: Authentication

AuthController → AuthService / AuthServiceImpl → UserRepository

EndpointAuthRequestSuccessFailure
POST /api/auth/login—{ username, password }200 → LoginResponseDto{ token, expiresAtUtc }401 {"message":"Invalid username or password"}
POST /api/auth/register—{ username, password, role }200 {"message":"User created successfully"}400 with a validation error list, or {"message":"Username already exists"}

What RegisterRequestValidator checks

  • username is required, and at most 50 characters.
  • password must be at least 8 characters.
  • role must case-insensitively match Admin, Staff, or Student — anything else fails validation before the service layer is ever reached.

What AuthServiceImpl does

Login: looks the user up by username; if found, compares the submitted password against the stored hash with PasswordEncoder.matches() — a constant-time comparison, deliberately never a plain == or .equals() on hashes, which would leak timing information an attacker could exploit. On a match, JwtUtil issues a token carrying the user's id, username, and role as claims.

Register: rejects a duplicate username, parses the requested role string into the UserRole enum (case-insensitively), hashes the password with BCrypt, and saves the new User row. No login token is issued at registration — the new user signs in separately afterward.

Where the three demo accounts come from

DataSeeder (a CommandLineRunner) runs once, automatically, right after Flyway creates the schema on startup, and creates admin / staff / student (all password Admin123!) if they don't already exist. These aren't seeded via the SQL migration like the demo courses and student are, because a real BCrypt hash has to be computed in Java at runtime — it can't be hand-typed into a migration file.

Module: Students

StudentController → StudentService / StudentServiceImpl → StudentRepository

EndpointAuthBehavior
GET /api/student—All students.
GET /api/student/{id}—One student, or 404.
POST /api/studentAdmin / Staff201 with the created StudentDto, or 400 with validation errors.
PUT /api/student/{id}Admin / Staff204 No Content, or 404 if the id doesn't exist.
DELETE /api/student/{id}Admin204, or 404. Cascades to that student's enrollments (JPA cascade + a DB-level ON DELETE CASCADE, belt-and-suspenders).

What StudentCreateValidator / StudentUpdateValidator check

  • firstName / lastName required, at most 50 characters each.
  • email required, must match a standard local@domain.tld shape.
  • dateOfBirth required, must match the DD/MM/YYYY shape, and — this is the interesting part — must be a real calendar date.
TWhy date validation needs more than a regex

A shape-only pattern like \d{2}/\d{2}/\d{4} accepts 31/04/2005 just as happily as 15/03/2005 — April only has 30 days, so the first one isn't a real date at all. Once the shape matches, the value is parsed with a DateTimeFormatter.ofPattern("dd/MM/uuuu").withResolverStyle(ResolverStyle.STRICT). STRICT resolution makes java.time's own calendar rules — days-per-month, leap years — do the real validation; an impossible date throws a DateTimeParseException, which the validator turns into a clear message rather than silently accepting bad data. (Note the pattern uses uuuu, the era-neutral year field, rather than yyyy — required for STRICT mode to work correctly with a plain LocalDate.) A future date is rejected separately, after a successful parse.

The eager-loading example that exists but isn't wired up

StudentRepository.findWithEnrollments(id) uses a JOIN FETCH query to eagerly load a student together with their enrollments and each enrollment's course, in one query — avoiding the N+1 query problem a naive lazy-load loop would hit. It's not called from any controller endpoint today; it exists purely as a documented, ready-to-use example of the pattern.

Module: Enrollments

EnrollmentController → EnrollmentService / EnrollmentServiceImpl → EnrollmentRepository, StudentRepository, CourseRepository

This is the most involved module — it's the join entity connecting the other two, and the only service class that's @Transactional.

EndpointAuthBehavior
GET /api/enrollment—All enrollments.
GET /api/enrollment/{id}—One enrollment, or 404.
GET /api/enrollment/student/{studentId}—Every enrollment (and grade) for one student.
POST /api/enrollmentAdmin / Staff{ studentId, courseId } — grade is intentionally not part of creation.
PUT /api/enrollment/{id}Admin / Staff{ grade } — assigns or updates the grade on an existing enrollment.
DELETE /api/enrollment/{id}Admin

Creating an enrollment: two independent existence checks

EnrollmentCreateValidator only checks that both studentId and courseId are non-null — whether they refer to real rows is a database question, not a shape-validation one. EnrollmentServiceImpl.create() looks up the student, then the course; if either lookup fails, it returns a typed EnrollmentCreateResult(success, error, enrollment) rather than a plain boolean, so the controller — and ultimately the dashboard's error message — can say specifically "Student not found" or "Course not found" instead of a generic failure.

Setting a grade

EnrollmentUpdateValidator requires a non-blank grade matching ^[A-Fa-f][+-]?$ — a single letter A through F, with an optional trailing + or - (so A, B+, C-, and f are all accepted; A++ or Pass are not).

TWhy this is the one @Transactional service

EnrollmentDto is deliberately flat — it carries studentName and courseName as plain strings rather than nesting full StudentDto/CourseDto objects (the same "DTOs are never the raw entity, and never over-nested" philosophy used everywhere in this codebase). Building those denormalized fields means toDto() has to call enrollment.getStudent().getFirstName() and enrollment.getCourse().getName() — both LAZY @ManyToOne associations. With spring.jpa.open-in-view=false set in application.properties (deliberately not Spring Boot's default), a lazy association can only be read while a transaction is still open. Without EnrollmentServiceImpl being @Transactional at the class level, that read would throw LazyInitializationException the moment the implicit request-scoped transaction closed. Keeping open-in-view=false and adding an explicit, narrow transaction boundary here — rather than leaving one transaction open for an entire HTTP request, which is what open-in-view=true does — is the standard, deliberately-chosen pairing.

Dashboard Architecture

The browser-based front end — how it's built, and how it talks to the API

PIn plain English

The dashboard is a normal web page — no app to install, nothing to build. It's the same three files a website was made of twenty years ago: one HTML file, one CSS file, one JavaScript file. Clicking around ("Students", "Courses"...) never actually reloads the page; JavaScript swaps out the content in place and talks to the server behind the scenes.

TTechnical framing

The dashboard is a same-origin static resource — src/main/resources/static/ — served directly by the same Spring Boot process at /. Because it's same-origin with the API, there's no CORS configuration, no second server process, and no build tooling (no bundler, no npm install). It's a genuine single-page application (SPA), just hand-written rather than framework-generated.

The three files

index.html

Markup for two states: the auth view (login + register forms) and the app shell (top nav, a single empty <main> the router fills in, and the footer). Both exist in the DOM at once; one is hidden at a time.

css/style.css

All visual design — dark theme, animated gradient background "orbs", glass-panel cards, the color-coded role badges and grade badges seen throughout the walkthrough below.

js/app.js

Everything else: session storage, the API client wrapper, the router, and one render function per page. No external libraries — plain DOM APIs and template literals.

Session & the API client

After login, the app stores { token, username, role, expiresAtUtc } in the browser's sessionStorage under the key qacademy_session — deliberately sessionStorage, not localStorage, so the session clears when the tab closes rather than persisting indefinitely. username and role are read straight off the JWT's own payload (base64-decoded client-side, no signature check needed here — the server re-validates the signature independently on every request that matters).

Every API call goes through one small wrapper, API.request(path, { method, body, auth }), which: attaches Authorization: Bearer <token> when auth: true is passed; turns any non-2xx response into a thrown Error with a human-readable .message (a 401 becomes "Your session has expired…", a 403 becomes "You don't have permission to do that…", and a validation-error array from the backend gets joined into one readable string); and throws a distinct network-failure message if the fetch itself can't reach the server at all.

Routing

A tiny hash-based router: { home, students, courses, enrollments } map route names to render functions, window.location.hash drives which one is active, and a hashchange listener re-renders <main> on every navigation — including the browser's own Back/Forward buttons, for free.

The exact same permission rules, mirrored client-side

Two tiny helper functions, canWrite() (role is Admin or Staff) and isAdmin() (role is Admin), gate every form and delete button the dashboard renders — deliberately mirroring the server's own @PreAuthorize rules one-for-one.

!This is UX, not the security boundary

Hiding a button client-side is a courtesy to the user, never the actual defense. If someone re-enabled a hidden "Delete" button through their browser's devtools, the request would still hit the real API — which would still reject it with 403 Forbidden, because the enforcement lives in @PreAuthorize on the server, not in what the dashboard chooses to render. The screenshots in the next section make this dual enforcement visible: the same page, rendered two different ways for two different roles.

Installation & Setup

Getting a working copy running locally, on macOS or Windows

Prerequisites

  • Java Development Kit (JDK) 17 — pinned deliberately, see Design Decisions.
  • Apache Maven 3.8+ — builds the project and manages dependencies.
  • Git — to clone the repository.

An IDE is optional: IntelliJ IDEA Community, Eclipse for Enterprise Java, or VS Code with the Java Extension Pack all work. Node.js and npm are not needed at all — the dashboard is plain HTML/CSS/JS.

1. Clone

git clone https://github.com/goodtogo01/qacademy.git
cd qAcademy

2. Install prerequisites

macOS (Homebrew)

brew install openjdk@17 maven git
sudo ln -sfn /opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk \
  /Library/Java/JavaVirtualMachines/openjdk-17.jdk
java -version   # confirm 17.x
mvn -version

Windows (winget, elevated PowerShell)

winget install --id EclipseAdoptium.Temurin.17.JDK
winget install --id Apache.Maven
winget install --id Git.Git
java -version
mvn -version

3. Build & test

mvn clean install

Compiles the project and runs the TestNG/Mockito unit suite. Expect BUILD SUCCESS.

4. Run it

mvn spring-boot:run

Wait for a line like Tomcat started on port 8085, then open http://localhost:8085/ — you'll land on the qAcademy sign-in screen.

PTroubleshooting, in plain terms

"Database may be already in use": another copy of the app is still running somewhere and hasn't fully stopped — find and stop that process, then try again. Dashboard edits not showing up: Spring Boot serves a compiled copy of the static files, not the live folder — stop the app (Ctrl+C) and start it again to pick up changes. Port already taken: change server.port in application.properties.

Design Decisions

The choices that were made on purpose, and why — the kind of thing worth being able to explain in an interview

Spring Boot 3.5, not 4.x

4.x requires Java 21 and brings several breaking changes (Jakarta-only namespaces, Hibernate 7, Jackson 3, new Spring Security 7 CSRF defaults) that couldn't be compiler-verified without a local build environment during initial development. Upgrading to 4.x afterward is a well-scoped exercise on its own — see Future Roadmap.

JwtAuthenticationFilter isn't a @Component

Covered in full in Security — a bean assignable to Filter gets auto-registered as a blanket servlet filter on top of whatever Spring Security wires via addFilterBefore(), running it twice per request. Constructed directly instead.

EnrollmentServiceImpl is class-level @Transactional

Paired deliberately with spring.jpa.open-in-view=false (not Boot's default). A lazy @ManyToOne association can only be read inside an active transaction; the DTO mapping needs to read student.getFirstName() / course.getName(), so the service method needs its own transaction spanning both the repository call and the mapping.

No Jakarta Bean Validation, no Lombok

Validation is hand-rolled Validator classes called explicitly from controllers, and entities have hand-written getters/setters. More boilerplate, but nothing hidden behind annotation processing — every line is something you can point to and explain.

Single Maven module, package-based layering

core / infrastructure / api instead of a multi-module reactor — the right tradeoff for one deployable of this size.

The dashboard is a same-origin static resource

Not a separate app — served by the same Spring Boot process at /, so it never needs CORS configuration or a second server. SecurityConfig explicitly permitAlls /, /index.html, /css/**, and /js/** alongside the Swagger/H2-console rules.

Future Roadmap

What's deliberately not built yet — concrete next steps, not vague ideas

PIn plain English

Nothing below is a bug — these are places the project stops on purpose, either because they were out of scope for a first version, or because they make good, well-scoped practice exercises for whoever picks this project up next.

  • A DELETE /api/course/{id} endpoint — the one asymmetry in the CRUD surface today: Students and Enrollments can be deleted, Courses cannot. Wiring this in (backend endpoint + dashboard button) is the most immediately obvious next step.
  • Refresh tokens instead of a flat 2-hour JWT expiry, so a signed-in user isn't forced to log in again mid-session.
  • Pagination, search, and filtering on the Students/Courses/Enrollments lists — fine at demo scale, would need this at real scale.
  • spring-boot-devtools for automatic restarts on code changes during development.
  • Containerization with Docker (a Dockerfile + docker-compose.yml), swapping H2 for Postgres for a production-shaped setup.
  • A live deployed demo (Render, Railway, or Fly.io all have free tiers suited to a Spring Boot + file-DB app of this size) — this is the "publish it to the cloud" step planned for later.
  • Upgrade to Spring Boot 4.x / Java 21 — a scoped, well-understood migration exercise once a compiler is available to verify the breaking changes against.
