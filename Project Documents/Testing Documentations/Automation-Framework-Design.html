Automation Framework Design

qAcademy — School Management System. How the automation framework is actually structured, why each design decision was made, and what changed since the original pre-implementation skeleton.

00  What Changed Since v1.0

Skeleton → implemented

v1.0 was written before a single line of automation code existed, explicitly scoped as "no implementation yet, per your request." Since then the framework described in that skeleton was built in full — every package, every class, every step in the original build order — and two things were added that v1.0 didn't anticipate, both driven by getting ready for a real CI/CD pipeline (Jenkins) rather than just local mvn test runs on a laptop:

  1. BackendLifecycleManager (§5, new package core.backend) — the app now auto-starts itself if a test run begins without it already running.
  2. Headless-by-default Chrome in CI (§6) — DriverFactory now detects a CI environment and launches Chrome headless automatically.

Everything else below is v1.0's design, updated to describe what's actually in the repository rather than what was planned, plus the two additions above and one bug-fix pattern worth calling out (§6.2). The src/main vs src/test decision in v1.0 §0 was followed exactly as designed — no changes there.

01  Maven Dependencies (as built)

All three dependencies from v1.0 are in pom.xml, test scope, alongside the pre-existing testng and mockito-core entries:

▪selenium-java

UI automation. Selenium Manager (built in since 4.6) resolves ChromeDriver/GeckoDriver automatically — no WebDriverManager dependency needed.

▪rest-assured

API automation. Deserializes straight into POJOs shaped like the app's own DTOs.

▪extentreports

HTML reporting, wired through ExtentReportManager and TestListener.

Surefire is wired to a single suite file:

<suiteXmlFiles>
    <suiteXmlFile>src/test/resources/testing/testng-regression.xml</suiteXmlFile>
</suiteXmlFiles>

testng-regression.xml combines testng-ui.xml, testng-api.xml, and testng-e2e.xml via <suite-files>, so a plain mvn test (or mvn clean verify, what the GitHub Actions workflow runs) executes the full regression pass. testng-smoke.xml is a separate, narrower suite for a fast confidence check and isn't wired into Surefire's default — point at it explicitly when you want a quick pass instead of the full run.

03  Java Concepts (unchanged from v1.0, confirmed against the built code)

The concept table below describes the framework as actually built, with no changes from the original design. Two more instances of patterns already in this table showed up in the additions in §5: BackendLifecycleManager is a Singleton (same justification as ExtentReportManager/ConfigManager), and BackendNotAvailableException is a custom unchecked exception in the same family as the FrameworkException pattern.

ConceptWhere it shows upWhy it's the right tool here
Page Object Modelui/pages/*Locators and low-level Selenium calls live in one place per screen; tests only call intention-revealing methods (loginPage.loginAs(ADMIN)) — a UI change means editing one Page class, not every test that touches that screen.
InheritanceBaseTest → BaseUiTest/BaseApiTest; BasePage → pagesShared setup/teardown and helpers live once at the top of the hierarchy instead of being copy-pasted.
Factory MethodDriverFactory.createDriver()Test code asks for "a Chrome driver" without knowing how it's constructed — swapping browsers later is a one-line change in the factory.
SingletonExtentReportManager, ConfigManager, BackendLifecycleManagerExactly one instance must exist per run — one report file, one loaded config, one backend process.
ThreadLocal<WebDriver>DriverManagerThe one Java concept that makes parallel UI execution safe — each thread gets its own driver without passing it through every method call.
Builder / fluent chainingRestAssured given()/when(); TestDataFactoryReads as a sentence; hand-written builders keep every line explainable, no generated code.
Fluent page navigationPage methods returning the next page objectA test reads as a story, and the compiler catches a broken navigation assumption immediately.
EnumsUserRole, Environment, BrowserTypeType-safe constants instead of raw strings — can't typo UserRole.ADMIN the way "admni" could be typo'd.
InterfacesApiClient contractLets shared utilities depend on a contract, not a concrete class.
Custom exceptionsBackendNotAvailableExceptionTurns a raw low-level exception into a message that says what business action actually failed.
ITestListenerTestListenerTestNG's reflection-based hook — logs, screenshots, and reports on test outcomes without a line of that logic inside the tests themselves.
Deterministic cleanup@AfterMethod in BaseUiTestA browser session closes whether the test above it passed or threw.
Streams / lambdastests/e2e/CrossLayerFlowTestWhere "combine UI and API" becomes concrete — comparing API data against UI-scraped data in a few lines.

04  Build Order — Status

All 16 steps from v1.0's build order are complete. Step 16 (layering BDD/Cucumber on top) remains explicitly out of scope, as designed — "later, per your stated intention, not part of this phase." Nothing in this update changes that; it's still a future decision, not a current gap.

05  Addition: BackendLifecycleManager

Not in v1.0

Problem this solves: before this existed, clicking Run on a test suite without first running mvn spring-boot:run produced one confusing failure per test class — a browser-level "site can't be reached" for every UI test, a raw ConnectException for every API test — with nothing pointing at the real cause.

What it does, wired into BaseTest's @BeforeSuite/@AfterSuite

  1. Sends a real HTTP request to an open, database-backed endpoint (ApiEndpoints.COURSE by default) — deliberately not just a TCP port check, since a bound port can exist before Spring has finished wiring the context, running Flyway migrations, or seeding demo data.
  2. If that succeeds, does nothing else — the common case, costing one fast HTTP call.
  3. If it fails, launches the backend itself (mvn spring-boot:run by default, overridable) as a background process, and polls the same health check every 2 seconds until it answers or backend.startupTimeoutSeconds (default 90s) is reached.
  4. If it still isn't up, fails the whole suite immediately with one clear BackendNotAvailableException pointing at target/automation-logs/backend-console.log.

Ownership rule

It only ever stops a backend it started itself (shutdownIfStartedByUs() is a no-op if the backend was already running) — so it never kills an instance you're running yourself for manual exploration alongside the suite. A JVM shutdown hook also guards against an orphaned backend process if the suite itself is killed before @AfterSuite runs.

Config keys (config.properties, all optional with hardcoded defaults): backend.autoStart, backend.autoStop, backend.startupTimeoutSeconds, backend.projectDir, backend.startCommand, backend.healthCheckPath.

Documented in full, with a diagram-adjacent explanation, in the Test-Blueprint under "01 Shared Foundation."

06  Hardening for CI/CD

Not in v1.0

Two changes made specifically so the suite behaves the same on a Jenkins build agent as it does on a laptop — both also written up in the Test-Blueprint's "Hardening for CI/CD" section.

6.1  Headless by default in CI

DriverFactory previously always launched a visible Chrome window — fine on a laptop, fatal on a build agent with no display. ConfigManager.isHeadless() now resolves to true automatically whenever config.properties' env=CI, or a GITHUB_ACTIONS / JENKINS_URL / CI environment variable is present (set by the build agent itself, not something a Jenkinsfile has to configure) — and can still be forced either way with headless=true/false. When headless, DriverFactory adds --headless=new, --window-size=1920,1080, --no-sandbox, --disable-dev-shm-usage, and --disable-gpu to ChromeOptions (Firefox gets -headless), and skips .maximize(). A local mvn test keeps showing the real browser exactly as before.

Why this mattered

The existing .github/workflows/ci.yml already runs mvn -B clean verify on ubuntu-latest on every push — before this fix, every UI test in that pipeline would have failed for lack of a display, and the same would have been true the moment a Jenkins agent ran the suite. Resolved for both.

6.2  Identity-based assertions, not row counts

One UI test, EnrollmentsPageTest.enrollStudent_withValidStudentAndCourse_addRow, asserted a table row-count delta against a table that's never reset between runs. Reliable on a fresh CI database on first run, but increasingly likely to race its own accumulated history across repeated local runs — which is what actually happened (a TimeoutException diagnosed and fixed this cycle). It now waits for its own uniquely-named row to appear by content, the same pattern its sibling assertions in the same test class already used. Worth calling out as a convention for any new UI test added later: assert identity, not counts, on any table/list that isn't reset between test runs.

A second, unrelated bug fixed in the same pass: testng-smoke.xml referenced a test method name that had a typo in the actual @Test method (AuthApiTest), so the smoke suite was silently skipping that case instead of running it. Both the method name and one misleading test name (a test asserting an invalid role was named as if it tested a short password) were corrected.

07  Still Deliberately Not Decided

Unchanged from v1.0

Exact TestNG @DataProvider usage for data-driven cases, whether EnrollmentsPage's inline grade editor needs its own small sub-component class, and the precise ExtentSparkReporter theme/branding remain open — none of these blocked getting to a working, CI-ready suite, and none are needed before the GitHub push or the Jenkins setup that follows it.

08  Status Relative to Your Next Steps

You said the next steps, in order, are: push to GitHub, then set up Jenkins CI/CD. As of this update, the framework itself has no known blocker for either — the two CI-specific gaps found during this review (headless support, the flaky assertion) are both fixed.
